# Chaos test results

Fault-injection tests in `tests/e2e/chaos_test.go` (helpers in `tests/e2e/internal/chaos`). Run with `make chaos` (needs `make dev`; it stops and starts services and the Kafka and Postgres containers, so the stack must be unused). Run on 2026-10-09, local stack (Windows, Docker Desktop, single Kafka node, one Postgres), swap on the default `PAYMENT_DEADLINE` (2m) except scenario 7 (25 s).

Every scenario runs the real agreement flow (user-2 negotiates user-1's ad, user-3 opens a competing negotiation on the same ad, both legs by locker) with a fault injected, then checks, from the APIs and from the databases: exactly one swap row for the negotiation and for the ad pair, at most one active or completed swap on the ad, swap/ad/`ad_lock`/negotiation statuses agree (for example `AWAITING_PAYMENT` means both ads `locked`, locks `locked`, negotiation `AGREED`), the competitor is `CANCELLED` (one winner) and no ad is stuck `LOCKED` without an `AWAITING_PAYMENT` swap. Where it applies the flow is then finished (both fees paid, swap `COMPLETED`, ads `CLOSED`).

Times: "converge" is measured from the moment the fault ends (service port open, container healthy) until the locked state is visible. Stopping a service means `taskkill` of its process tree, so a killed Kafka consumer does not leave its group; the restarted consumer waits for the group rebalance (session timeout, seen up to ~35 s). Starting a service through `scripts/dev.sh start` includes a rebuild (9-12 s for .NET). Convergence timeout in the tests: 90 s.

## Findings

One real bug was found (finding 6, fixed). Observations and documentation points:

1. **Group rebalance dominates recovery.** After a service is killed, its consumer group needs the session timeout (up to ~45 s) before the restarted instance is assigned its partitions. Scenario 1 took 66 s from agreement to restart and 34 s more to converge; scenario 2 showed that nothing happens in the swap for ~20 s after it is started (first run of the scenario found no `Handler failed` line and no swap row after 20 s, so the test now waits for the failure line before bringing Ad back). A client sees `AGREEMENT_PENDING` for that long after a swap restart. Doc impact: the failure-behavior table in the architecture document now has a row for it.
2. **Failure-behavior row "Crash after LockAds committed": confirmed in effect** by scenario 2 (swap `LOCKING`, retried, `LockAds` idempotent after Ad returns); the exact crash window (after the lock commit, before the swap update) was not injected.
3. **Duplicate `AgreementReached` with a fresh `event_id` is not deduplicated by `processed_events`** (the row count grows by one) but the handler is a no-op for a swap that is not `LOCKING`, as documented. Each such duplicate leaves one `processed_events` row; harmless.
4. **Documentation updated afterwards:** the architecture document's failure-behavior section and Known gap 14 now cite these scenarios and list what was not run (the claim "none of this was exercised by a fault-injection test" was removed).
5. **Not covered:** `ExclusiveLockAcquired` waiting while negotiation is down (cannot be timed deterministically; the kill would race the consumer), a crash between the outbox produce and `published_at`, killing the single Kafka node with data loss.
6. **Lost `MatchFound` under parallel consumers (bug, fixed).** Scenario 8 found that when two compatible ads are applied at the same time (different partitions, handled in parallel with `CONSUMER_CONCURRENCY` above 1, or by two instances), each transaction upserts its ad, neither sees the other's uncommitted row when it queries candidates, and no `MatchFound` is produced for the pair although the index is correct. The ordering assumption was true for the old sequential consumer only. Fix: `ApplySnapshot` takes a transaction-scoped advisory lock (`pg_advisory_xact_lock`) before indexing, so the second transaction queries after the first has committed; regression test `TestConcurrentApplyOfCompatibleAdsStillNotifies` fails without it. Cost: index updates in matching are serialized per database.

Logs of each stopped service are kept in `.run/chaos-logs/` (the service log is truncated on each start); one result line per scenario is appended to `.run/chaos-results.txt`.
